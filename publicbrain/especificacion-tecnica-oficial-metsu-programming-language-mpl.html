Especificación de Arquitectura Runtime Standalone de MPL (Metsu Programming Language)

1. Visión General de la Arquitectura MPL

El lenguaje MPL (Metsu Programming Language) es un lenguaje de especificación y programación estructurado en capas jerárquicas de abstracción. Su objetivo principal es permitir la representación continua de sistemas software desde su descripción declarativa orientada a requisitos de usuario hasta su ejecución lógica e imperativa.

2. Definición Formal de las Capas de Abstracción

2.1. Capa URD (User Requirements Definition)

  • Definición: Especificación semántica formalizada en castellano (es-ES) sin construcciones sintácticas rígidas de código.
  • Propósito: Capturar la intención del dominio, reglas de negocio, flujos de experiencia de usuario (UX) y estados globales del sistema.

2.2. Capa 3: Pseudocódigo de Alto Nivel (Human-Centric DSL)

  • Definición: DSL declarativo con lexemas formales en español.
  • Construcciones Principales: PANTALLA, VISTA, OPCION, CUANDO, TRANSICIONAR_A, MOSTRAR, SOLICITAR.
  • Propósito: Mapear directamente la topología de la aplicación, las decisiones del usuario y las transiciones de estado.

2.3. Capa 2: Objetos Conceptuales e Interacciones

  • Definición: Capa orientada a entidades de dominio, modelos de datos, máquinas de estado y buses de comunicación.
  • Construcciones Principales: OBJETO_CONCEPTUAL, ESTADO, EVENTO, PROPAGAR, SUSCRIBIR, CONEXION.
  • Propósito: Formalizar los modelos de información y el desacoplamiento mediante patrones de eventos/señales.

2.4. Capa 1: Pseudocódigo Formal Imperativo

  • Definición: Lenguaje estructurado de control de flujo imperativo, tipos de datos fuertemente tipados y funciones primitivas.
  • Construcciones Principales: FUNCION, VARIABLE, SI...SINO, MIENTRAS, PARA, RETORNAR, INCAPSULAR.
  • Propósito: Proporcionar la base ejecutable determinista subyacente.

5. Especificación Sintáctica por Capas (Sintaxis Canónica)

5.1. Ejemplo Sintáctico: Capa 3 (DSL Declarativo)

PANTALLA VistaPrincipal:
    ENCABEZADO: "MetsuOS Terminal v1.0"

    COMPONENTE MenuOpciones:
        OPCION "1. Cargar Recurso" CON_ACCION CargarRecurso
        OPCION "2. Consultar Estado" CON_ACCION ConsultarEstado
        OPCION "3. Finalizar" CON_ACCION Salir

    CUANDO AL_PULSAR_TECLA(Escape):
        TRANSICIONAR_A VistaSalida

5.2. Ejemplo Sintáctico: Capa 2 (Objetos y Eventos)

OBJETO_CONCEPTUAL GestorRecursos:
    PROPIEDADES:
        identificador: Cadena
        activo: Booleano
        metadatos: Diccionario[Cadena, Cadena]

    EVENTOS:
        EventoRecursoCargado(id: Cadena)

    INTERACCIONES:
        METODO inicializar(id: Cadena):
            ESTADO.activo = Verdadero
            DISPARAR EventoRecursoCargado(id)

5.3. Ejemplo Sintáctico: Capa 1 (Imperativo Formal)

FUNCION ValidarYProcesarEntrada(entrada: cadena) -> booleano:
    VARIABLE es_valida: booleano
    es_valida = Falso

    SI Longitud(entrada) > 0 ENTONCES:
        VARIABLE i: entero
        PARA i = 0 HASTA Longitud(entrada) - 1 HACER:
            SI CaracterEn(entrada, i) == ' ' ENTONCES:
                RETORNAR Falso
            FIN_SI
        FIN_PARA
        es_valida = Verdadero
    SINO:
        es_valida = Falso
    FIN_SI

    RETORNAR es_valida
FIN_FUNCION

SeccionEncabezado  ::= "ENCABEZADO" ":" Cadena ;

TriggerUI          ::= "AL_PULSAR_TECLA" "(" Identificador ")" | "AL_SELECCIONAR" "(" Identificador ")" ;
AccionUI           ::= "TRANSICIONAR_A" Identificador | "EJECUTAR" Identificador ;

6.2. Reglas EBNF: Capa 2 (Objetos Conceptuales y Bus de Eventos)

ProgramaC2            ::= { DefinicionObjeto } ;

DefinicionObjeto      ::= "OBJETO_CONCEPTUAL" Identificador ":" [ BloquePropiedades ] [ BloqueEventos ] [ BloqueInteracciones ] ;

BloquePropiedades     ::= "PROPIEDADES" ":" { DeclaracionPropiedad } ;
DeclaracionPropiedad  ::= Identificador ":" TipoDatoC2 ;

BloqueEventos         ::= "EVENTOS" ":" { DeclaracionEvento } ;
DeclaracionEvento     ::= Identificador "(" [ ListaParametrosC2 ] ")" ;

BloqueInteracciones   ::= "INTERACCIONES" ":" { DefinicionMetodo } ;
DefinicionMetodo      ::= "METODO" Identificador "(" [ ListaParametrosC2 ] ")" ":" { SentenciaC2 } ;

SentenciaC2           ::= AsignacionEstado | DisparoEvento | InvocacionC1 ;
AsignacionEstado      ::= "ESTADO" "." Identificador "=" Expresion ;
DisparoEvento         ::= "DISPARAR" Identificador "(" [ ListaArgumentos ] ")" ;
InvocacionC1          ::= Identificador "(" [ ListaArgumentos ] ")" ;

TipoDatoC2            ::= "Texto" | "Numero" | "Booleano" | "Coleccion" | "Diccionario" "[" TipoDatoC2 "," TipoDatoC2 "]" ;

6.3. Reglas EBNF: Capa 1 (Imperativo Formal)

ProgramaC1          ::= { DefinicionFuncion | DeclaracionGlobal } ;

DefinicionFuncion   ::= "FUNCION" Identificador "(" [ ListaParametrosC1 ] ")" [ "->" TipoDatoC1 ] ":" BloqueSentencias "FIN_FUNCION" ;

ListaParametrosC1   ::= ParametroC1 { "," ParametroC1 } ;
ParametroC1         ::= Identificador ":" TipoDatoC1 ;

BloqueSentencias    ::= { SentenciaC1 } ;

SentenciaC1         ::= DeclaracionVariable
                      | Asignacion
                      | Condicional
                      | BucleMientras
                      | BuclePara
                      | Retorno ;

DeclaracionVariable ::= "VARIABLE" Identificador ":" TipoDatoC1 [ "=" Expresion ] ;
Asignacion          ::= Identificador "=" Expresion ;

Condicional         ::= "SI" Expresion "ENTONCES" ":" BloqueSentencias [ "SINO" ":" BloqueSentencias ] "FIN_SI" ;
BucleMientras       ::= "MIENTRAS" Expresion "HACER" ":" BloqueSentencias "FIN_MIENTRAS" ;
BuclePara           ::= "PARA" Identificador "=" Expresion "HASTA" Expresion "HACER" ":" BloqueSentencias "FIN_PARA" ;

Retorno             ::= "RETORNAR" Expresion ;

TipoDatoC1          ::= "cadena" | "entero" | "decimal" | "booleano" | "arreglo" "[" TipoDatoC1 "]" ;

8. Mecanismo de Transpilación y Semántica de Compilación

El proceso de compilación en MPL no genera directamente lenguaje máquina; transforma las representaciones de alto nivel mediante pasadas de análisis semántico hasta consolidar un AST (Abstract Syntax Tree) ejecutable de Capa 1.

sequenceDiagram

    participant Parser as Analizador Sintáctico

    participant Transpiler as Generador AST MPL
    participant Target as Target de Ejecución

    Parser->>Semantico: Entrega Árbol Sintáctico C3 / C2 / C1
    Note over Semantico: Valida referencias cruzadas entre
Acciones de UI y Métodos C2

    Note over Transpiler: Reduce abstracciones de C3 y C2

    Transpiler->>Target: Emite AST Consolidado Capa 1

8.1. Pasadas del Compilador MPL

  1. Pasada 1 (Lexing y Parsing): Convierte el código fuente escrito en cualquier capa de MPL en nodos del AST correspondiente.
  2. Pasada 2 (Resolución de Símbolos): Mapea los identificadores de UI en Capa 3 con sus correspondientes métodos/eventos en Capa 2, y las invocaciones de Capa 2 con funciones de Capa 1.
  3. Pasada 3 (Lowering / Descenso de Capa): Traduce de forma autómata las estructuras declarativas (PANTALLA, OBJETO_CONCEPTUAL) a bucles de eventos imperativos y estructuras de datos en Capa 1.
  4. Pasada 4 (Emisión): Generación del ejecutable final o representación intermedia para el runtime objetivo de MetsuOS.

9. Especificación del Runtime y Event Loop (Motor de Ejecución)

El runtime de MPL opera bajo una arquitectura de ejecución híbrida impulsada por eventos (Event-Driven Loop). Las construcciones declarativas de la Capa 3 y los eventos de la Capa 2 se traducen en un ciclo de eventos no bloqueante en la Capa 1.

11.1. Modelo de Concurrencia y Asincronía

  • Aislamiento de Estado: Los objetos conceptuales (Capa 2) gestionan su estado de forma aislada.
  • Canales de Comunicación: La interacción entre entidades se realiza mediante el paso de mensajes asincrónicos o el disparo directo de eventos (DISPARAR).
  • Primitivas Asincrónicas (Capa 1):
  • ESPERAR: Pausa la ejecución de la rutina actual cediendo el control al Event Loop hasta que se resuelva una promesa o evento.
  • EN_SEGUNDO_PLANO: Ejecuta un bloque imperativo sin bloquear el hilo principal.

10. Manejo de Excepciones y Propagación Cruzada de Errores

El sistema de errores de MPL es uniforme a través de todas las capas, permitiendo capturar fallos técnicos de bajo nivel (Capa 1) o errores de estado/dominio (Capa 2) y representarlos de forma amigable en la interfaz (Capa 3).

sequenceDiagram
    autonumber
    participant C1 as Capa 1 (Imperativo)
    participant C2 as Capa 2 (Objeto / Estado)
    participant C3 as Capa 3 (DSL UI)

    Note over C1: Error I/O o Condición Inválida
    C1->>C1: LANZAR_ERROR ExcepcionLectura
    C1-->>C2: Propaga Excepción no capturada

    Note over C2: Intercepta error en Método
    C2->>C2: PROPAGAR_ERROR ErrorDominio
    C2-->>C3: Notifica fallo de acción

    Note over C3: Captura evento en UI
    C3->>C3: MOSTRAR_AVISO "Error de Procesamiento"

10.1. Sintaxis Canónica de Manejo de Errores

Capa 1: Captura Técnica Imperativa

INTENTAR:
    VARIABLE resultado: cadena
    resultado = LeerArchivo(ruta)
CAPTURAR ExcepcionArchivoNoEncontrado COMO error:
    Imprimir("Error de lectura: " + error.mensaje)
    RETORNAR Falso
FIN_INTENTAR

Capa 2: Propagación Semántica de Dominio

OBJETO_CONCEPTUAL GestorArchivos:
    INTERACCIONES:
        METODO procesar_documento(ruta: Texto):
            INTENTAR:
                EjecutarLectura(ruta)
            CAPTURAR ErrorTecnico COMO e:
                PROPAGAR_ERROR ErrorNegocio("El documento no se pudo validar.")

12. Modelo de Memoria y Ciclo de Vida de Objetos

MPL adopta un esquema de gestión de memoria basado en Conteo de Referencias con Recolector de Ciclos (ARC/Garbage Collector híbrido) en la Capa 1, completamente transparente para el desarrollador en las Capas 2 y 3.

  • Creación de Instancias: Ocurre automáticamente al entrar en un estado de la Capa 3 o al invocar un OBJETO_CONCEPTUAL en la Capa 2.
  • Destrucción de Instancias: Cuando un objeto o vista deja de estar activo o referenciado en el árbol de contexto, el runtime libera de forma determinista sus recursos e invoca su destructor implícito AL_DESTRUIR.
OBJETO_CONCEPTUAL SesionUsuario:
    PROPIEDADES:
        token: Texto

    INTERACCIONES:
        METODO AL_CREAR():
            ESTADO.token = GenerarToken()

        METODO AL_DESTRUIR():
            LimpiarMesaTrabajo()

13.1. Pruebas Unitarias en Capa 1 (Imperativo Formal)

Las pruebas de Capa 1 verifican la corrección determinista de las funciones y algoritmos puros mediante aserciones estrictas.

PRUEBA "Validación de formato de cadena no vacía":
    VARIABLE entrada: cadena
    entrada = "MetsuOS"

    VARIABLE resultado: booleano
    resultado = ValidarYProcesarEntrada(entrada)

    AFIRMAR_VERDADERO(resultado)
    AFIRMAR_IGUAL(Longitud(entrada), 7)
FIN_PRUEBA

13.2. Pruebas de Integración y Estado en Capa 2 (Objetos y Eventos)

Las pruebas de Capa 2 verifican la mutación de propiedades de un OBJETO_CONCEPTUAL, la correcta emisión de eventos y el manejo de excepciones de dominio.

PRUEBA "Ciclo de vida y emisión de eventos en GestorRecursos":
    VARIABLE gestor: GestorRecursos

    ESCUCHAR_EVENTO gestor.EventoRecursoCargado COMO evento_capturado

    gestor.inicializar("RES-001")

    AFIRMAR_VERDADERO(gestor.PROPIEDADES.activo)
    AFIRMAR_IGUAL(gestor.PROPIEDADES.identificador, "RES-001")
    AFIRMAR_EVENTO_DISPARADO(evento_capturado)
FIN_PRUEBA

13.3. Pruebas de Interfaz y Flujo de Usuario en Capa 3 (DSL Declarativo)

Las pruebas de Capa 3 simulan la interacción del usuario sobre pantallas y componentes para verificar el comportamiento de la experiencia de usuario (UX).

PRUEBA "Navegación desde VistaPrincipal por pulsación de tecla":
    CARGAR_PANTALLA VistaPrincipal

    SIMULAR_PULSAR_TECLA(Escape)

    AFIRMAR_PANTALLA_ACTIVA(VistaSalida)
FIN_PRUEBA

13.4. Sintaxis y Primitivas de Aserción Nativas

Primitiva de AserciónCapa aplicableDescripción
AFIRMAR_IGUAL(v1, v2)Capa 1, 2, 3Verifica la igualdad de valor o referencia entre dos expresiones.

16.1. Metsu Intermediate Representation (MIR)

MIR es la representación intermedia de tipo SSA (Static Single Assignment) en la que se reducen todas las construcciones de las tres capas a un grafo de flujo de control linealizado.

  • Instrucciones en tres direcciones (3AC): Las llamadas a eventos de Capa 2 y transiciones de Capa 3 quedan aplanadas a instrucciones condicionales y saltos de bloque.
  • Optimizaciones del Compiler Pass:
  • Dead Code Elimination: Eliminación de vistas o componentes no transitados en Capa 3.
  • Inlining de Métodos: Inserción directa de métodos C1 en eventos C2 de alta frecuencia.
  • Análisis de Duración de Variables: Minimización del impacto del Garbage Collector/ARC.

Sobre la categorización de los tipos de conocimiento

  • Conocimiento Gnoseológico: ⚫① 🔴② 🟡③ 🟢④

La Metsukeología (de Metsuke vision global y logos conocimiento) es la ciencia que estudia el conocimiento como un conjunto potencial de conocimiento del que podemos obtener, procesar o percibir partes concretas dentro de un marco contextual específico, y cuyo contexto general real está muy por encima de lo que somos capaces, como especie, de percibir, procesar e integrar de forma completa (definición en progreso).

La Metsucología (de Metsu aniquilación - en este contexto en forma de colapso - , logos conocimiento) es la ciencia que estudia como extraemos verdades percibidas - colapsadas - como conocimiento desde nuestra perspectiva real (tanto epistemológico como gnoseológico) al tomar una parte específica del conocimiento metsukeológico potencial enmarcado en un contexto concreto, obligando a colapsar el conocimiento potencial en conocimiento específico (definición en progreso).
